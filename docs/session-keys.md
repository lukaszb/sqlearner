# Session keys and event history

Use **Save session key** while a session is open to save a portable `.sqlr` text file. Use **Restore session key** on either screen to create a new local session. Import never overwrites an existing session. The file contains a `SQLR1.<sha256>.<base64url-gzip>` key; SHA-256 detects accidental corruption, not malicious editing. Keys are not encrypted and contain SQL, results and database contents.

The version 1 payload includes a stable random session seed, session metadata, the ordered event history, and consistent SQLite backups of both `olist.sqlite` and `practice.sqlite`. Full database snapshots preserve arbitrary writes, partially successful SQL batches and nondeterministic statements without executing historical SQL during import. This makes the key substantially larger than a short identifier. Export and decoded payloads have a 1 GiB limit. A short remote lookup key would require a storage service, which this local format does not use.

`session-events.jsonl` is the source of truth for progress and workspace state. Its header carries the version and seed. Events have a monotonically increasing sequence, timestamp, type and payload. Session I/O is serialized, and appended events are flushed before acknowledgement. State updates contain the complete affected projection; replay applies them in sequence. Semantic UI events retain action arguments, quiz questions and option ordering, selected answers, failed and successful attempts, SQL results and errors. Query drafts, query tabs, selected tables, lesson drafts, quiz navigation, hint and solution visibility, and progress survive restart and export. Pointer movement, hover and scroll are not recorded.

The first event imports existing `lesson-progress.json` and `workspace-state.json` as a baseline. Earlier interactions cannot be reconstructed if an older version did not record them. After migration, these JSON files are compatibility snapshots, not authoritative state. Missing or malformed journals fail visibly rather than silently resetting progress. Import rebuilds these snapshots by replaying the journal. Actual question snapshots remain authoritative across course changes; future draws use the seed and persisted draw count.

The event log and SQLite writes are separate durable resources, not one atomic transaction. An interrupted SQL request may have changed the database without a corresponding success event; database snapshots preserve the actual database state. Corrupt or truncated event logs require recovery rather than automatic truncation. History grows without compaction to retain previous interactions.
